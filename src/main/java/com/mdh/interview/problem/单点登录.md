# 单点登录

## 方案
| 方案 | 核心协议/技术 | 适用场景 | 优点 | 缺点 |
| :--- | :--- | :--- | :--- | :--- |
| CAS | CAS Protocol | 企业内部系统、高校、传统 Web 应用 | 协议成熟，开源社区活跃（Apereo），Java 集成非常方便。 | 主要是重定向模式，对前后端分离（SPA）支持不够友好<websource>source_group_web_2</websource>。 |
| OAuth2 / OIDC | OAuth 2.0 / OpenID Connect | 互联网应用、微服务、第三方登录（微信/钉钉） | 行业标准，支持移动端和前后端分离，生态最丰富（Keycloak, Auth0）<websource>source_group_web_3</websource>。 | 实现逻辑相对复杂，OIDC 在 OAuth2 基础上增加了身份认证层<websource>source_group_web_4</websource>。 |
| SAML 2.0 | SAML (XML) | 跨国企业、大型传统机构（如银行） | 安全性极高，行业标准，支持复杂的身份联邦<websource>source_group_web_5</websource>。 | 配置繁琐，基于 XML 报文，体积大，解析慢，开发调试困难<websource>source_group_web_6</websource>。 |
| 自研 (JWT) | JWT + Redis | 微服务架构、轻量级系统 | 无状态，性能高，完全可控，适合 Spring Cloud 体系<websource>source_group_web_7</websource>。 | 需要自己处理安全性（如注销、刷新），非标准协议<websource>source_group_web_8</websource>。 |



## 网关 + JWT（微服务架构）
~~~
Spring Cloud Gateway + JWT（微服务架构）

架构设计：
    1.认证服务 (Auth Service)：负责登录，校验账号密码，生成 JWT (JSON Web Token) 并存入 Redis。
    2.API 网关 (Gateway)：全局拦截。检查请求头中的 Authorization 字段。
    3.业务服务：不再处理登录逻辑，只信任网关透传的用户信息（如 X-User-Id）。
关键实践：
    1.无状态：JWT 包含用户信息，服务端不存 Session（或仅在 Redis 存黑名单用于注销）。
    2.双 Token 机制：使用 Access Token (短效) 和 Refresh Token (长效) 来平衡安全与体验。
~~~
