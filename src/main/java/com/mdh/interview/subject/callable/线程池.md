## 线程中wait 和 sleep区别？
~~~
sleep属于Thread类中的static方法，              wait属于Object类方法
sleep属于TIMED_WAITING，自动被唤醒，           wait属于WAITING，需要手动唤醒
sleep方法在只有锁时，执行、不会释放锁资源         wait会在执行后，释放锁资源
sleep可以在持有或未持有锁时执行。                wait必须在持有锁的时候执行
~~~


## 线程池的优势
~~~
线程池做的工作主要是控制运行的线程的数量,处理过程中将任务放入队列,然后在线程创建后启动这些任务,如果线程数量超过了最大
数量,超出数量的线程排队等候,等其它线程执行完毕,再从队列中取出任务来执行。

主要特点: 线程复用,控制最大并发数,管理线程

第一: 降低资源消耗。通过重复利用已创建的线程降低线程创建和销毁造成的消耗。
第二: 提高响应速度。当任务到达时,任务可以不需要等到线程创建就能立即执行。
第三: 提高线程的可管理性。线程是稀缺资源,如果无限制的创建,不仅会消耗系统资源,还会降低系统的稳定性,使用线程池可以进
     行统一的分配,调优和监控
~~~

## 线程池的 5 种核心状态
| 状态名称 | 含义 | 接收新任务？ | 处理队列任务？ | 说明 |
| :--- | :--- |:-------|:--------| :--- |
| RUNNING | 运行中 | 是      | 是       | 线程池创建后的默认状态，正常工作。 |
| SHUTDOWN | 关闭 | 否      | 是       | 调用 `shutdown()` 后进入。不再接收新任务，但会坚持把队列里的旧任务做完，属于“温和”的关闭。 |
| STOP | 停止 |  否     |  否      | 调用 `shutdownNow()` 后进入。不仅拒绝新任务，还会中断正在执行的任务，并丢弃队列中等待的任务。 |
| TIDYING | 整理 | -      | -       | 过渡状态。当任务全部终止（队列空 + 线程数归零）时进入此状态，准备执行 `terminated()` 钩子方法。 |
| TERMINATED | 终止 | -      | -       | 最终状态。`terminated()` 方法执行完毕，线程池彻底销毁。 |

## 状态流转图解
~~~
1.正常关闭流程（温和）
    RUNNING → (调用 shutdown()) → SHUTDOWN → (任务处理完) → TIDYING → (钩子执行完) → TERMINATED

2.强制关闭流程（暴力）
    RUNNING → (调用 shutdownNow()) → STOP → (中断任务) → TIDYING → (钩子执行完) → TERMINATED
~~~

## 线程池的原理
~~~
1. ctl 的精妙设计
线程池并没有用两个变量分别存储“状态”和“线程数”，而是用了一个 AtomicInteger 类型的 ctl 变量：
    高 3 位：存储运行状态（如 RUNNING, STOP 等）。
    低 29 位：存储工作线程数量（WorkerCount）。

    为什么要这样？
        为了保证原子性。在并发环境下，如果状态和线程数分开存储，可能会出现“状态变了但线程数没变”的中间状态，导致逻辑混乱。通过 CAS 操作一次性更新 ctl，既节省内存又保证了线程安全。

2. SHUTDOWN vs STOP 的区别
    SHUTDOWN (优雅停机)：适用于 Web 服务器关闭等场景。它允许已提交的任务执行完毕，保证业务数据的完整性。
    STOP (立即停机)：适用于紧急故障处理。它会尝试通过 Thread.interrupt() 中断正在运行的线程，并且直接清空等待队列，不再浪费资源。

3. TIDYING 的作用
    这是一个“中间人”状态。当线程池满足以下条件时进入此状态：
        状态是 SHUTDOWN 且 队列和线程池都为空；
        或者 状态是 STOP 且 线程池为空。
    进入 TIDYING 后，线程池会调用 terminated() 方法（这是一个空实现的钩子方法，你可以重写它来做资源清理），执行完后才会变成 TERMINATED。
~~~



## 线程池复用
~~~
线程池实现“线程复用”的核心秘密在于：工作线程（Worker）在完成任务后不会立即销毁，而是进入一个“无限循环”，持续从任务队列中获取新任务。

1. 核心载体：Worker 类
在 Java 的 ThreadPoolExecutor 中，线程并不是直接运行任务的，而是被封装成了一个内部类——Worker。
    继承 AQS：Worker 类继承了 AbstractQueuedSynchronizer（AQS），这使得它可以利用 AQS 的独占锁机制来标记线程是否正在执行任务（防止在任务执行中被中断）。
    持有线程：Worker 内部持有一个真正的 Thread 对象。
    持有任务：Worker 启动时会绑定一个“首个任务”（firstTask）。
    
2. 复用的核心逻辑：runWorker 的死循环
这是线程复用最关键的代码逻辑。当 Worker 启动后，会执行 runWorker() 方法。这个方法里包含了一个while 无限循环：

        final void runWorker(Worker w) {
            Runnable task = w.firstTask; // 1. 先执行启动时带来的第一个任务
            w.firstTask = null;
            
            // 2. 核心复用逻辑：死循环
            // 只要任务不为空，或者能从队列里获取到新任务，循环就永远不结束
            while (task != null || (task = getTask()) != null) {
                w.lock(); // 加锁，标记线程正在忙碌
                try {
                    task.run(); // 3. 执行具体的业务逻辑
                } finally {
                    w.unlock(); // 解锁，允许线程被中断或回收
                    task = null; // 4. 清空任务引用，准备下一次循环
                }
            }
            // 5. 只有当 getTask() 返回 null（超时或池关闭）时，才会跳出循环，执行线程回收
            processWorkerExit(w, completedAbruptly);
        }

    复用流程图解：
        1.执行任务：线程执行完 task.run()。
        2.清空状态：将 task 置为 null。
        3.再次获取：进入 while 判断，调用 getTask()。
        4.阻塞等待：如果队列没任务，getTask() 会让线程阻塞（挂起），释放 CPU，但不销毁线程。
        5.唤醒执行：一旦有新任务提交到队列，线程被唤醒，拿到任务，再次执行 task.run()。

3.获取任务的策略：getTask()
    getTask() 方法决定了线程是“永久存活”还是“超时死亡”：
        核心线程（Core Pool）：默认情况下，核心线程调用队列的 take() 方法。这是一个阻塞操作，如果没有任务，线程会一直等下去，永不过期。这就是为什么核心线程可以一直复用的原因。
        非核心线程（Maximum Pool）：非核心线程调用队列的 poll(keepAliveTime) 方法。这是一个带超时的阻塞操作。如果超过指定时间（如 60秒）还没等到新任务，getTask() 返回 null，循环结束，线程自我销毁。

4.为什么要复用？（底层成本）
    因为线程是重量级资源：
        内存成本高：每个线程启动都需要分配独立的虚拟机栈（默认 1MB 左右）和本地内存。
        CPU 成本高：线程的创建和销毁涉及系统调用，且过多的线程会导致频繁的上下文切换（Context Switch），消耗大量 CPU 资源。
        JVM 负担：每个线程都是 GC Root，过多线程会增加垃圾回收的复杂度。
        
总结
线程池的复用不是魔法，而是通过“死循环 + 阻塞队列”实现的：线程执行完任务后，不退出，而是通过 getTask() 阻塞在队列上等待下一个任务。这种机制极大地减少了线程创建和销毁的开销，实现了资源的高效利用。
~~~


## 为什么使用线程池？
~~~
并发编程中，对于常见的操作系统，线程都是执行任务的基本单元，如果每次执行任务时都创建新的线程，任务执行完毕又进行销毁，会出现以下的问题：


1.资源开销：比如在Linux系统中，频繁的创建和销毁线程，一个是频繁的进行一个系统调用，另外是一些内存和CPU资源调度的占用。
    虽然有一些写时复制的策略防止lwp的创建时的内存占用，但是实际写入还是会申请系统内存的，何况一些页表等本身就有内存占用。
2.性能瓶颈：线程的创建需要系统调用，如果只是简单的计算任务，可能耗时还没创建的rt高，这里反而降低了系统的吞吐量。
3.缺乏资源管理：无限制的创建线程会导致内存溢出，java.lang.OutOfMemoryError: unable to create native thread，
    这里主要因为Java的线程其实Linux中是lwp线程，需要通过JNI进行系统调用创建，每个线程默认需要1MB的栈空间，很容易导致无休止的创建线程导致内存溢出，
    另外就是频繁的系统调用，导致的上下文切换，占用了过多的CPU，反而起到了相反的作用。
4.功能受限：手动管理线程难以实现更高级的功能，如定时任务、周期任务、任务管理、并发任务数的控制等。

通过上面的问题，我们其实可以清晰的感知到这些问题都是归拢到资源没有得到合理的分配和控制导致的，线程池出现的核心宗旨其实就是对资源的合理分配和控制。
除了线程池，其实更多的也接触过数据库连接池、netty的对象池等池化技术，这些池化思想其实都是为了更好的降低资源的消耗以及更好的进行资源管理。
~~~


## java提供的线程池有五种
~~~
重点三个:
Executors.newFixedThreadPool(int nThreads) (定长线程池);  执行长期的任务,性能好 
public static ExecutorService newFixedThreadPool(int nThreads) {
        return new ThreadPoolExecutor(nThreads,   (int corePoolSize)
                                      nThreads,   (int maximumPoolSize)
                                      0L,
                                      TimeUnit.MILLISECONDS,
                                      new LinkedBlockingQueue<Runnable>());
    }
1. 创建一个定长线程池,可控制线程最大并发数量,超出的线程会在队列中等待。
2. newFixedThreadPool创建的线程池corePoolSize和maximumPoolSize值是相等的,使用LinkedBlockingQueue<Runnable>()


Executors.newSingleThreadExecutor() (单线程); 一个任务一个任务执行的场景
public static ExecutorService newSingleThreadExecutor() {
        return new FinalizableDelegatedExecutorService
            (new ThreadPoolExecutor(1, 1,
                                    0L, TimeUnit.MILLISECONDS,
                                    new LinkedBlockingQueue<Runnable>()));
    }
1. 创建一个单线程的线程池,它只会用唯一的工作线程来完成任务,保证所有任务按照指定顺序执行。
2. newSingleThreadExecutor将corePoolSize和maximumPoolSize都设置成1,它使用的LinkedBlockingQueue<Runnable>()


Executors.newCachedThreadPool() (可缓存线程); 执行很多短期异步的小程序或者负载较轻的服务
public static ExecutorService newCachedThreadPool() {
        return new ThreadPoolExecutor(0, Integer.MAX_VALUE,
                                      60L, TimeUnit.SECONDS,
                                      new SynchronousQueue<Runnable>());
    }
1. 创建一个可缓存线程池,如果线程池长度超过处理需要,可灵活回收空闲线程,若无可回收,则新建线程。
2. newCachedThreadPool将corePoolSize设置为0,将maximumPoolSize设置为Integer.MAX_VALUE,使用SynchronousQueue<Runnable>()
    也就是说来了任务就会创建线程运行,当线程空闲超过60秒,就销毁线程
    
    
定时及周期执行:
Executors.newScheduledThreadPool(int corePoolSize, ThreadFactory threadFactory);
    该线程池可以执行定时任务和周期性任务，也可以提交普通的异步任务。
    

java8 里面:
Executors.newWorkStealingPool(int parallelism);
java8新增,使用目前机器上可用的处理器作为它的并行级别

通过Executors.newVirtualThreadPerTaskExecutor()来创建虚拟线程
~~~

## 线程池使用
~~~
public class ThreadPoolUtils {
    private static volatile ExecutorService threadPool = null;

    public static ExecutorService getThreadPool() {
        if (threadPool == null) {
            synchronized (ThreadPoolUtils.class) {
                if (threadPool == null) {
                    ThreadFactory threadFactory = new ThreadFactoryBuilder()
                            .setUncaughtExceptionHandler((t, e) -> ExceptionLogUtil.printException(e, "多线程执行异常"))
                            .setNameFormat("steps-complete-thread-%d").build();
                    BlockingQueue<Runnable> workingQueue = new ArrayBlockingQueue<>(100000);
                    ThreadPoolExecutor executorService = new ThreadPoolExecutor(30, 30, 1000, TimeUnit.MILLISECONDS, workingQueue, threadFactory);
                    threadPool = TtlExecutors.getTtlExecutorService(executorService);
                }
            }
        }
        return threadPool;
    }
}

## 重要参数
~~~
public ThreadPoolExecutor(int corePoolSize,
                              int maximumPoolSize,
                              long keepAliveTime,
                              TimeUnit unit,
                              BlockingQueue<Runnable> workQueue,
                              ThreadFactory threadFactory,
                              RejectedExecutionHandler handler) {
        if (corePoolSize < 0 ||
            maximumPoolSize <= 0 ||
            maximumPoolSize < corePoolSize ||
            keepAliveTime < 0)
            throw new IllegalArgumentException();
        if (workQueue == null || threadFactory == null || handler == null)
            throw new NullPointerException();
        this.corePoolSize = corePoolSize;
        this.maximumPoolSize = maximumPoolSize;
        this.workQueue = workQueue;
        this.keepAliveTime = unit.toNanos(keepAliveTime);
        this.threadFactory = threadFactory;
        this.handler = handler;
    }

1. corePoolSize: 线程池中的常驻核心线程数
2. maximumPoolSize: 线程池能够容纳同事执行的最大线程数,此值必须大于等于1
3. keepAliveTime: 多余的空闲线程的存活时间
        当前线程池数量超过corePoolSize时,当空闲时间达到keepAliveTime值时,
        多余空闲线程会被销毁直到只剩下corePoolSize个线程为止
4. unit: keepAliveTime的时间单位
5. workQueue: 任务队列,被提交但尚未被执行的任务
6. threadFactory: 表示生成线程池中工作线程的线程工厂,用于创建线程一般用默认的额即可
7. handler: 拒绝策略,表示当前队列满了并且工作线程大于等于线程池的最大线程数(maximumPoolSize)时如何拒绝
    四个拒绝策略全部实现了 RejectedExecutionHandler接口
    AbortPolicy(默认): 直接抛出RejectedExecutionException异常阻止系统正常运行。
    CallerRunsPolicy: "调用者运行"一种调节机制,该策略既不会抛弃任务,也不会抛出异常,而是将某些任务回退到调用者,从而降低新任务的流量。
    DiscardOldestPolicy: 抛弃队列中等待最久的任务,然后把当前任务加入队列中尝试再次提交当前任务。
    DiscardPolicy: 直接抛弃任务,不予任何处理也不抛出异常。如果允许任务丢失,这是最好的一种方案。


线程池的底层工作原理
1. 在创建了线程池后,等待提交过来的任务请求。
2. 当调用execute()方法添加一个请求任务时,线程池会做如下判断:
    2.1 如果正在运行的线程数量小于corePoolSize,那么马上创建线程运行这个任务;
    2.2 如果正在运行的线程数量大于等于corePoolSize,那么将这个放入队列;
    2.3 如果这时候队列满了且正在运行的线程数量还小于maximumPoolSize,那么还是要创建非核心线程立刻执行这个任务;
    2.4 如果队列满了且正在运行的线程数量大于或等于maximumPoolSize,那么线程池会启动饱和拒绝策略来执行.
3. 当一个线程完成任务时,它会从队列中去下一个任务来执行。
4. 当一个线程空闲超过一定的时间(keepAliveTime)时,线程池会判断:
    如果当前运行的线程大于corePoolSize,那么这个线程就被停掉。
    所以线程池的所有任务完成后它最终会收缩到corePoolSize的大小。
~~~

## ThreadPoolExecutor扩展
~~~
ThreadPoolExecutor扩展主要是围绕beforeExecute()、afterExecute()和terminated()三个接口实现的，
1、beforeExecute：线程池中任务运行前执行
2、afterExecute：线程池中任务运行完毕后执行
3、terminated：线程池退出后执行
通过这三个接口我们可以监控每个任务的开始和结束时间，或者其他一些功能。
~~~


## 工作中的线程池配置
~~~
Runtime.getRuntime().availableProcessors() CPU核心数

CPU密集型(for循环做计算)
    CPU密集的意思是该任务需要大量的运算,而没有阻塞,CPU一直告诉全速运行。
    CPU密集任务只能在真正的多核CPU上才能得到加速(通过多线程)

    CPU密集型任务配置尽可能少的线程数量:(每核一个减少切换)
    一般公式:CPU核数 + 1个线程的线程池

IO密集型(数据库,redis取数据 大量的IO操作)
    (书本上介绍的)由于IO密集型任务线程并不是一直在执行任务,则应该配置尽可能多的线程,如CPU核数*2
    或者
    (大厂的实例)IO密集型,即改任务需要大量的IO,即大量的阻塞
    在单线程上运行IO密集型的任务会导致浪费大量的CPU运算能力浪费在等待。
    所以在IO密集型任务中使用多线程可以大大的加速程序运行,即使在单核CPU上,这种加速主要就是利用了被浪费掉的阻塞时间。
    IO密集型时,大部分线程都阻塞,故需要多配制线程数:
    
    参考公式: CPU核数/1 - 阻塞系数       阻塞系数在0.8 ~ 0.9之间
    比如8核CPU: 8/1-0.9 = 80 个线程数
    
    
CPU密集型任务： CPU核心数+1
I/O密集型任务： 2*CPU核心数
线程数 = CPU核心数 * （1 + 线程等待时间/线程运行时间）  线程等待时间：指的就是线程没有使用CPU的时间，比如阻塞在了IO    线程运行时间：线程执行完某个任务的总时间

## 线程池都有哪些状态？
~~~
private final AtomicInteger ctl = new AtomicInteger(ctlOf(RUNNING, 0)); 
维护了线程池的状态（高3位） 和 工作线程的个数（低29位）

RUNNING -1：这是最正常的状态，接受新的任务，处理等待队列中的任务。
SHUTDOWN 0：不接受新的任务提交，但是会继续处理等待队列中的任务。
STOP 1：不接受新的任务提交，不再处理等待队列中的任务，中断正在执行任务的线程。
TIDYING 2：所有的任务都销毁了，workCount 为 0，线程池的状态在转换为 TIDYING 状态时，会执行钩子方法 terminated()。
TERMINATED 3：terminated()方法结束后，线程池的状态就会变成这个。
~~~

## 线程池添加工作线程的流程？
~~~
addWorker
1.校验线程池的状态以及工作线程个数
2.添加工作线程并启动工作线程
	通过cas保证原子性去增加ctl第29位的值，所有判断都通过后，在new Worker()方法创建Worker， 
	在把worker放到hashSet集合中，再通过worker中的thread对象，执行start()方法，启动当前工作线程
~~~

## 线程池中 submit() 和 execute() 方法有什么区别？
~~~
execute()：只能执行 Runnable 类型的任务。
submit()：可以执行 Runnable 和 Callable类型的任务。
Callable 类型的任务可以获取执行的返回值，而 Runnable 执行无返回值。
~~~

## 线程池使用完毕为何必须shutdown()?
~~~
1.工作线程都是基于thread 执行start()启动线程，线程会占用虚拟机栈，根据可达性分析，这样核心线程不能被回收，造成内存泄漏
2.启动的线程还是指向worker对象，worker对象属于线程池的内部类，不会回收，线程池对象也不会被回收，也会造成内存泄漏

shutdown()： 将线程池的状态设置为shutdown，并不会立即停止
1.停止接受外部submit的任务
2.内部正在跑的任务和队列里等待的任务，会执行完
3. 等到第二部完成后，才真正停止
  非核心 通过 workQueue.poll(keepAliveTime, TimeUnit.MAN) 阻塞一段时间
  核心 通过 workQueue.take() 会阻塞， interruptIdWorkers（）方法，把所有的没有在运行任务的工作线程，设置中断标记位为true。线程结束。

shutdownNow()：将线程池的状态设置为stop， 一般会立即停止，实际上不一定
1.先停止接受外部提交的任务
2.忽略队列的等待的任务
3.尝试将正在跑的任务interrupt中断
4.返回未执行的任务列表

shutdown() 和 shutdownNow() 区别：
shutdownNow： 能立即停止线程池，正在跑的和正在等待的任务都停下来。这样做立即生效，但风险很大
shutdown：只是关闭了提交通道，用submit()是无效的； 而内部的任务该还是在跑的，跑完才会彻底停止线程池。
~~~

## 线程池异常处理方式
~~~
1. try-catch 捕获异常
2.实例化时，传入自己的ThreadFactory，设置 Thread.UncaughtExceptionHandler处理未检测的异常
3.重写ThreadPoolExecutor.afterExecute方法，处理传递的异常引用
4.submit执行，Future.get 接受异常
~~~

2.共享变量 不常用
	volatile boolean flag = true;

		while(flag){

		}

	通过Thread.currentThread.isInterrupted() 获取
