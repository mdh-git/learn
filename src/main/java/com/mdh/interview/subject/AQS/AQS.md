## 原理
~~~
AQS核心思想是,如果被请求的共享资源空闲,则将当前请求资源的线程设置为有效的工作线程,并且将共享资源设置为锁定状态。
如果被请求的共享资源被占用,那么久需要一套线程阻塞等待以及被唤醒时锁分配的机制,
这个机制AQS是用CLH队列锁实现的,即将暂时获取不到锁的线程加入到队列中。

AQS使用一个volatile的int类型的成员变量来完成同步状态,通过内置的FIFO队列来完成资源获取的排队工作
将每条要去抢占资源的线程封装成一个Node节点来实现锁的分配,通过CAS完成对State值的修改。


CLH(Craig,Landin,and Hagersten)队列是一个虚拟的双向队列(虚拟的双向队列即不存在队列实例,仅存在节点之间的关联关系)
AQS是将每条请求共享资源的线程封装成一个CLH锁队列的一个结点(Node)来实现锁的分配。


AQS（多线程中的队列同步器） = volatile state + FIFO 队列（基于CLH变体的FIFO先进先出）单向自旋/阻塞队列） + 模板方法


1.是多线程中的队列同步器。是一种锁机制，它是做为一个基础框架使用的像ReentrantLock、Semaphore都是基于AQS实现的
2.AQS内部维护了一个先进先出的双向队列，队列中存储的排队的线程
3.在AQS内部还有一个属性state，这个state就相当于是一个资源，默认是0(无锁状态)，如果队列中的有一个线程修改成功了state为1，则当前线程就相等于获取了资源
4.在对state修改的时候使用的cas操作，保证多个线程修改的情况下原子性
~~~

## 核心数据结构
~~~
State（资源状态）：内部维护了一个 `volatile int state` 变量。
        比如 ReentrantLock 中，state=0 代表无锁，state>0 代表有锁及重入次数。
        比如 Semaphore 中，state 代表剩余信号量的数量。
    CLH 队列（等待队列）：当线程抢不到资源（State）时，AQS 会把该线程封装成一个 Node 节点，扔到一个 FIFO 的双向链表中排队挂起。
~~~

## 核心工作流程
~~~
加锁（Acquire）：尝试用 CAS 操作修改 state。
        * 如果成功，拿锁走人。
        * 如果失败，封装成 Node 入队，并调用 `LockSupport.park()` 让线程阻塞。
解锁（Release）：修改 state（通常是减 1）。
        * 如果 state 归零，表示锁彻底释放，AQS 会唤醒（unpark）队列头部的线程去抢锁。
~~~

## 设计模式
~~~
AQS 使用了模板方法模式 (Template Method Pattern)。它封装了排队、阻塞、唤醒等复杂的底层逻辑，子类（如 ReentrantLock）只需要实现 `tryAcquire` 和 `tryRelease` 等简单的方法来定义‘什么是获取成功，什么是释放成功’即可。
~~~

## AQS 底层使用了模板方法模式
~~~
同步器的设计是基于模板方法模式的，如果需要自定义同步器一般的方式是这样（模板方法模式很经典的一个应用）：

（1）使用者继承 AbstractQueuedSynchronizer 并重写指定的方法。（这些重写方法很简单，无非是对于共享资源 state 的获取和释放）
（2）将 AQS 组合在自定义同步组件的实现中，并调用其模板方法，而这些模板方法会调用使用者重写的方法。


AQS 使用了模板方法模式，自定义同步器时需要重写下面几个 AQS 提供的模板方法：

isHeldExclusively()//该线程是否正在独占资源。只有用到condition才需要去实现它。
tryAcquire(int)//独占方式。尝试获取资源，成功则返回true，失败则返回false。
tryRelease(int)//独占方式。尝试释放资源，成功则返回true，失败则返回false。
tryAcquireShared(int)//共享方式。尝试获取资源。负数表示失败；0表示成功，但没有剩余可用资源；正数表示成功，且有剩余资源。
tryReleaseShared(int)//共享方式。尝试释放资源，成功则返回true，失败则返回false。
~~~

## AQS采用双向链表
~~~
AQS（AbstractQueuedSynchronizer）的同步队列之所以采用双向链表，而不是单向链表或数组，主要是为了在高并发场景下实现高效的节点删除、状态回溯以及无锁化操作。

AQS 是 ReentrantLock、CountDownLatch 等并发工具的基石，其核心是一个由 Node 节点组成的 FIFO 双向队列。以下是 AQS 采用双向链表的三个核心原因：

1.高效删除节点（O(1) 时间复杂度）
    在并发环境中，排队的线程可能会因为超时或被中断而放弃竞争锁。此时，AQS 需要将该线程对应的节点从队列中移除。
        双向链表的优势：由于节点中保存了前驱节点（prev）的引用，当需要删除当前节点时，可以直接通过 prev 找到前驱节点，修改其 next 指针跳过当前节点。这个过程的时间复杂度是 O(1)。
        单向链表的劣势：如果是单向链表，节点只知道后继节点，不知道前驱节点。要删除当前节点，必须从头节点（Head）开始遍历链表，找到当前节点的前一个节点，时间复杂度是 O(n)。在长队列的高并发场景下，这会带来巨大的性能开销。
2.支持反向回溯，防止“锁死”
    这是 AQS 设计中最精妙的地方之一。当持有锁的线程释放锁时，它需要唤醒队列中的下一个节点。但是，队列中的后继节点可能处于取消状态（CANCELLED）（例如线程已中断）。
        双向回溯逻辑：AQS 在唤醒后继节点时（unparkSuccessor 方法），如果发现直接后继节点是无效的，它会利用双向链表的 prev 指针，从尾节点（Tail）开始向前遍历（反向回溯），找到第一个有效的等待节点进行唤醒。
        避免死锁：如果采用单向链表，一旦遇到连续的无效节点，系统可能无法找到后续的有效节点，导致没有线程被唤醒，从而引发锁死（Deadlock）。双向链表保证了无论队列中间有多少无效节点，都能可靠地找到下一个有效的等待者。
3.方便判断前驱状态（公平性与挂起）
    线程在入队后进入阻塞状态前，需要检查其前驱节点的状态，以决定是否应该挂起自己。
        判断前驱：线程需要确认它的前驱节点是否是头节点（Head），或者前驱节点的状态是否为 SIGNAL（表示前驱释放锁后会唤醒我）。
        直接访问：通过双向链表的 prev 指针，线程可以直接访问前驱节点进行判断。如果是单向链表，这又需要一次从头遍历的操作。

~~~

## 非公平锁
~~~
非公平锁流程：能插队就插队
非公平锁的策略是“贪婪”的，它的目标是尽最大可能获取锁，减少线程阻塞和唤醒的开销。
    步骤一：直接“插队” (lock 方法)
        线程调用 lock() 时，首先不检查队列，直接尝试通过 CAS 将 state 从 0 修改为 1。
            成功：直接获取锁，设置当前线程为独占线程。
            失败：说明锁被占用了，进入步骤二。
    步骤二：进入 AQS 标准流程 (acquire 方法)
        调用 AQS 的 acquire(1)。这会再次调用 tryAcquire。
    步骤三：再次尝试获取 (tryAcquire)
        即使是排队阶段，非公平锁的 tryAcquire 依然不检查队列。
            如果 state == 0，再次尝试 CAS 抢锁（这是第二次插队机会）。
            如果 state != 0 且当前线程已经持有锁，则重入（state + 1）。
            如果都失败，才调用 addWaiter 将自己包装成 Node 节点加入 CLH 队列尾部，并阻塞等待。
~~~

## 公平锁
~~~
公平锁流程：老老实实排队
公平锁的策略是“守规矩”的，它保证了先来后到。
    步骤一：直接进入排队逻辑 (lock 方法)
        线程调用 lock() 时，不做任何 CAS 尝试，直接调用 acquire(1)。这意味着它默认自己需要排队。
    步骤二：检查是否有前驱节点 (tryAcquire)
        在 tryAcquire 方法中，公平锁多了一个关键判断：hasQueuedPredecessors()。
            判断逻辑：检查 CLH 队列中，当前线程前面是否有其他线程在等待。
            如果有前驱：放弃抢锁，返回 false，进入排队流程（addWaiter）。
            如果没有前驱（队列为空，或者当前线程就是队头）：才尝试通过 CAS 修改 state 获取锁。
~~~

## 双向链表（CLH队列的变体）
~~~
“高效地处理节点取消”
“可靠地唤醒后继节点”

1. 高效移除节点
这是最直观的原因。在并发场景下，等待锁的线程可能会因为超时、被中断或主动取消而需要离开队列。
    单向链表的痛点：如果要删除一个中间节点，必须找到它的前驱节点（Predecessor）来修改 next 指针。单向链表无法直接获取前驱，必须从头节点（Head）开始遍历查找，时间复杂度为 O(n)。在高并发下，这会造成巨大的性能损耗。
    双向链表的优势：每个节点都持有 prev（前驱）和 next（后继）引用。当需要删除节点时，可以直接通过 node.prev 和 node.next 修改指针，将当前节点从链表中摘除，时间复杂度为 O(1)。
        // 双向链表删除节点只需两步（伪代码）
            node.prev.next = node.next; // 前驱指向后继
            node.next.prev = node.prev; // 后继指向前驱
            
2.可靠的唤醒机制（防止“唤醒丢失”）
这是最核心的技术约束。当持有锁的线程释放锁时，它需要唤醒队列中的下一个有效节点。

场景：假设队列结构是 Head -> A(已取消) -> B(有效) -> Tail。
    单向链表的死穴：释放锁的线程位于 Head，它查看 Head.next 发现是 A。因为 A 已取消，Head 需要跳过 A 去找 B。但在单向链表中，Head 无法直接知道 A 后面是谁（如果 A 的 next 指针因并发修改不一致），或者需要从头遍历。更严重的是，如果 A 正在被移除，单向链表极易出现断裂，导致 B 永远无法被唤醒（死锁）。
    双向链表的解法：AQS 的 unparkSuccessor 方法采用了一种“从尾向前回溯”的策略。
        如果发现 node.next 为空或已取消。
        它会从 Tail（尾节点） 开始，利用 prev 指针向前遍历。
        找到第一个状态正常（非取消）的节点（即节点 B）。
        唤醒 B。
            这种反向查找机制完全依赖于双向链表的 prev 指针，它能保证在存在大量取消节点的情况下，依然能找到那个“漏网之鱼”并唤醒它。
            
3.快速判断前驱状态
    线程在入队后，需要判断自己是否可以安全地挂起（Park）。这通常需要检查前驱节点的状态（例如前驱是否是头节点，或者前驱是否已取消）。
        单向链表：同样需要遍历查找前驱，效率低下。
        双向链表：直接通过 node.prev 获取前驱，瞬间完成判断。
~~~
