# 分布式事务

~~~
在分布式系统中一次操作需要由多个服务协同完成，这种由不同的服务之间通过网络协同完成的事务称为分布式事务
https://www.cnblogs.com/chengxy-nds/p/14046856.html
https://blog.csdn.net/a745233700/article/details/122402303
~~~

## 解决方案
~~~
1.本地消息表  本地事务 + 消息队列 + 最终一致性
    阶段一：业务与消息同一个数据库，在同一个事务中执行(保证原子性)
        事务发起方（如订单服务）在处理本地业务时，会在同一个本地数据库事务中完成两件事：
            1.执行核心业务逻辑（如更新订单状态为“已支付”）。
            2.向一张专门的“本地消息表”中插入一条待发送的消息记录。
    阶段二：异步可靠投递 (保证可靠性)
        务事务提交后，一个独立的定时任务或线程会周期性地扫描本地消息表，查找状态为 PENDING（待发送）的消息。
            1.将找到的消息投递到消息中间件（如 RocketMQ, Kafka）。
            2.如果投递成功，则更新消息表中的状态为 SENT（已发送）。
            3.如果投递失败，则保留 PENDING 状态，等待下一次轮询重试。通常会设置最大重试次数，超过后标记为“死亡消息”并告警，等待人工干预。
    这个机制确保了消息一定会被发送出去，即使发起方服务短暂宕机，重启后定时任务也能继续完成投递。
    阶段三：下游消费与幂等 (保证最终一致)
        下游服务（如库存服务）订阅消息中间件，接收到消息后执行自己的业务逻辑（如扣减库存）。
            消费者必须实现幂等性。
    
2.消息队列：
    目前RocketMQ中支持事务消息
    a.生产者订单系统先发送一条half消息到broker，half消息对消费者而言是不可见的
    b.在创建订单，根据创建订单成功与否，向Broker发送commit或者rollback
    c.并且生产者订单系统还可以提供Broker回调接口，当Broker发现一段时half消息没有收到任何操作命令，则会主动调用此接口来查询订单是否创建成功
    d.一旦half消息commit了，消费者库存系统就会来消费，如果消费成功，则消息撤销，分布式事务成功结束
    e.如果消费失败，则根据重试策略进行重试，最后还失败则进入死信队列，等待进一步处理
    
3.seata：阿里开源的分布式事务框架，支持AT、TCC等多种模式，底层都是基于两阶段提交理论来实现的
~~~

## 本地消息表
~~~
CREATE TABLE local_message (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    biz_id VARCHAR(64) NOT NULL COMMENT '业务唯一ID，用于幂等',
    topic VARCHAR(128) NOT NULL COMMENT '消息主题',
    content TEXT NOT NULL COMMENT '消息内容，通常为JSON格式',
    status VARCHAR(20) NOT NULL DEFAULT 'PENDING' COMMENT '状态: PENDING, SENT, COMPLETED, FAILED',
    retry_count INT DEFAULT 0 COMMENT '重试次数',
    create_time DATETIME NOT NULL,
    update_time DATETIME NOT NULL,
    INDEX idx_status_time (status, create_time) -- 关键索引，加速轮询
);
~~~
