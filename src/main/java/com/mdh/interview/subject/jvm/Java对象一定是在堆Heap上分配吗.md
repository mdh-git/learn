# Java对象一定是在堆Heap上分配吗?

~~~
不一定都是在堆上分配，可能是栈上分配
~~~

## 逃逸分析(Escape Analysis)
~~~
1.方法逃逸
    当对象被当做返回值返回，或者作为参数传递给其他方法，必须在堆上分配
    return new User();
    
2.线程逃逸
    对象赋值给变量、实例变量，被其他线程访问，必须在堆上分配
    static Obj = new User();
    
3.没有逃逸
    对象只在当前方法内部使用，作用域未扩散
    User u = new User();
    u.id = 1;
    这种方式有可能触发优化
~~~

## 标量替换(Scalar Replacement)
~~~
如果对象没有逃逸，JVM不创建对象，而是把它的成员变量拆开，直接当做局部变量放在栈帧里

// 源代码
Point p = new Point(1,2);
sout(p.x)

// JIT优化后(标量替换)
int x = 1;
int y = 2;
sout(x)

直接在线程栈中分配，并没有在堆中创建Point对象
~~~

## TLAB与栈上分配
~~~
TLAB(Thread Local Allocation Buffer)
    位置: 还是在堆(Eden)上
    机制: 每个线程在Eden预占一小块地方
    目的: 避免多线程分配时的锁竞争(无锁分配)
    GC: 需要GC回收
    
栈上分配(标量替换) 
    位置: 还栈帧(Stack Frame)上
    机制: 拆解对象，使用局部变量表
    目的: 完全避免堆分配，减轻GC压力
    GC: 无需GC回收(随方法出栈)
~~~

## 同步消除(Lock Elimination)
~~~
如果对象没有逃逸出线程，那么对它加锁是没有任何意义的(其他线程访问不到)。JVM就会去掉这个锁。
案例：线程StringBuffer性能跟非线程安全的Stringbuilder性能差不多
~~~

## JVM逃逸分析
~~~
1.逃逸分析是JIT C2编译器的优化。代码要执行足够多次，触发JIT编译器后生效。 短任务/Serverless 享受不到
2.只要有一点点可能逃逸，JVM就不敢优化，标量替换也不能处理太大的对象
3.分析本身也是成本，现在G1/ZGC 已经很快了，有时候逃逸分析带来的收益不是很明显


减少对象创建、复用对象池、合理配置GC参数、使用Arthas定位问题
~~~
