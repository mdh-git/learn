# GC耗时10毫秒为什么系统卡顿10秒

~~~
现象描述：
1.系统突然无响应
2.GC日志显示： Total time：10.01s
3.但真正的GC耗时： Real GC：0.01s
~~~

## JIT编译器
~~~
HosSpot JIT编译器认为int类型的计数循环（Counted Loop）运行极快，为了性能，它会溢出循环体内的SafePoint轮询。

int i(Trap)
for(int i = 0, i < 200000000;i++){
    // 纯计算
    // JIT: 这循环很快，去掉检查
    <SafePoint Check Striped>
}
后果：如果不跑完这20亿次，线程无法响应GC中断


改进

long i（Safe）
for(long i = 0, i < 200000000;i++){
    // 纯计算
    // JIT: long 太慢，不敢优化
    <SafePoint Check Striped>
}
后果：每次循环都会检查，随叫随停
利用HotSpot对long循环分析不充分的特性，强制保留SafePoint


正规做法
JVM参数
-XX:+UseCountedLoopSafepoints
强制JIT在计数循环中也插入SafePoint轮询。虽然牺牲一点点性能，保证了系统稳定性

~~~

## JVM 的两个机制
~~~
1.安全点 (SafePoint)
    当 JVM 需要执行某些全局性操作时（例如垃圾回收 GC、线程堆栈跟踪 jstack 等），它会要求所有应用线程暂停。
    线程不会立即暂停，而是会执行到下一个“安全点”才真正停下来。
    这个暂停所有线程的过程被称为 Stop-The-World (STW)。
    
2.JIT 编译器优化
    为了提升性能，JIT 编译器会进行各种优化。其中一项优化是：如果一个循环的迭代次数可以被确定（例如 for (int i = 0; i < 1000; i++)，这种循环被称为“可数循环”），编译器可能会认为它执行时间很短，从而移除循环内部的安全点检查，以减少不必要的开销。
~~~
