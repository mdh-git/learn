## 收集器总结

| 收集器             | 串行、并行or并发 | 新生代/老年代 | 算法               | 目标         | 适用场景                                  |
| ------------------ | ---------------- | ------------- | ------------------ | ------------ | ----------------------------------------- |
|               | 串行             | 新生代        | 复制算法           | 响应速度优先 | 单CPU环境下的Client模式                   |
| Serial  Old        | 串行             | 老年代        | 标记-整理          | 响应速度优先 | 单CPU环境下的Client模式、CMS的后备预案    |
| ParNew             | 并行             | 新生代        | 复制算法           | 响应速度优先 | 多CPU环境时在Server模式下与CMS配合        |
| Parallel  Scavenge | 并行             | 新生代        | 复制算法           | 吞吐量优先   | 在后台运算而不需要太多交互的任务          |
| Parallel  Old      | 并行             | 老年代        | 标记-整理          | 吞吐量优先   | 在后台运算而不需要太多交互的任务          |
| CMS                | 并发             | 老年代        | 标记-清除          | 响应速度优先 | 集中在互联网站或B/S系统服务端上的Java应用 |
| G1                 | 并发             | both          | 标记-整理+复制算法 | 响应速度优先 | 面向服务端应用，将来替换CMS               |

## 组合选择
~~~
单CPU或者小内存,单机程序
    -XX:+UseSerialGC

多CPU,需要最大量吞吐,如后台计算型应用(允许一点点停顿)
    -XX:+UsParallelGC  或者  -XX:+UseParallelOldGC

多CPU,追求低停顿时间,需要快速响应 如互联网应用
    -XX:UseConcMarkSwepGC  或者  -XX:+ParNewGC
~~~

## G1
~~~
G1是一种服务器端的垃圾收集器,应用在多处理器的大容量内存中,在实现高吞吐量的同时,尽可能的满足垃圾回收器暂时间的要去

像CMS收集器一样,能与应用程序并发执行
整理空闲空间更快
需要更多的时间来预测GC停顿时间
不希望牺牲大量的吞吐性能
不需要更大的Java Heap

G1是一个有整理内存过程的垃圾收集器,不会产生很多内存碎片。
G1的Stop The Wor(STW)更可控,G1在停顿时间上添加了预测机制用户可以指定期望停顿时间。

主要改变是Eden,Survivor和Tenured等内存区域不再是连续的
改变成一个个大小一样的region,每个region从1M到32M不等。一个region有可能属于Eden,Survivor或者Tenured内存区域

特点:
1.G1能充分利用多CPU、多环境硬件优势,尽量缩短STW。
2.G1在整体上采用标记-整理算法,局部是通过复制算法,不会产生内存碎片
3.宏观上看G1之中不在区分年轻代和老年代。把内存化成多个独立的子区域(Region)
4.G1收集器里面讲整个的内存区都混合在一起了,但其本事依然在小范围内要进行年轻代和老年代的区分,保留了新生代和老年代,
    但他们不再是物理隔离的,而是一部分Region的集合且不需要Region是连续的,也就是说依然会采用不同得到的GC方式来处理不同的区域。
5.G1虽然也是分代收集器,但整个内存分区不存在物理上的年轻代和老年代的区别,也不需要完全独立的survivor(to space)堆做复制准备。
    G1只有逻辑上的额分代概念,或者说每个区都可能随G1的运行在不用代之间前后切换。


配置参数:
-XX:+UseG1GC
-XX:G1HeapRegionSize=n  设置G1区域的大小。值是2的幂,范围是1MB到32MB。目标是根据最小的Java堆大小划分出约2048个区域。
-XX:MaxGCPauseMillis=n  最大GC停顿时间,这是个软目标,JVM将尽可能(但不保证)停顿小于这个时间
-XX:InitiatingHeapOccupancyPercent=n  堆占用了多少的时候就触达GC,默认为45
-XX:ConcGCThreads=n  并发GC使用的线程数
-XX:G1ReservePercent=n  设置作为空闲空间的预留内存百分比,以降低目标空间溢出的风险,默认值是10%
~~~

## G1与CMS对比
~~~
1:  G1不会产生内存碎片
2:  是可以精确控制停顿时间,该收集器是把整个堆(新生代、老年代)划分成多个固定大小的区域,每次根据允许停顿时间去收集垃圾最多的区域
~~~

##  分代收集算法-工作机制
~~~
1.新创建的对象，都会先分配到Eden区
2.当Eden区内存不足，标记Eden区与From（现阶段没有）的存活对象
3.将存活对象采用复制算法到To中，复制完成后，Eden区和From内存都得释放
4.经过一段时间后Eden区内存又出现不足，标记Eden区、To区存活的对象，将存活的对象复制到From区中
5.当幸存区对象被回收（最多15次），晋升到老年代（幸存区内存不足或者大对象会导致提前晋升）
~~~

##  对象晋升规则
~~~
年龄阈值：默认年龄达到 15（可通过 -XX:MaxTenuringThreshold 调整）晋升到老年代。
动态年龄判断：如果 Survivor 区中，同一年龄的所有对象大小总和超过 Survivor 空间的 50%，则大于等于该年龄的对象提前晋升。
大对象直接进入：超过 -XX:PretenureSizeThreshold 的对象直接在老年代分配。
        该功能默认是关闭的，该参数仅对 Serial Old 和 Parallel Scavenge + Parallel Old 收集器组合有效。
        G1 收集器忽略它：如果你使用的是 G1 GC（现代应用的主流选择），JVM 会完全忽略这个参数。
        G1 有自己的机制来处理大对象（Humongous 对象），它会根据 Region 的大小自动判断，如果对象大小超过 Region 容量的 50%，则直接分配为 Humongous 对象（逻辑上属于老年代，但物理上占用连续多个 Region）。
~~~

## JVM跨代引用处理
~~~
问题：如果只扫描新生代，如何保证不漏掉“老年代对象引用新生代对象”的情况？
    Minor GC只回收年轻代，如果老年代对象引用了年轻代对象

解决：引入 卡表 (Card Table)。(空间换时间)

机制：
    将老年代内存划分为若干个小的区域（Card，通常 512 字节）。
    维护一个卡表数组，每个元素对应一个 Card。
    当老年代对象修改引用指向新生代对象时（写屏障 Write Barrier），将对应的 Card 标记为“脏”（Dirty）。
GC 时：
    进行 Minor GC 时，GC Roots 不仅包含栈和本地变量，还包含卡表中被标记为“脏”的老年代对象。
    这样只需扫描少量的“脏卡”，而无需扫描整个老年代，极大提升了效率。
   
~~~

## 标记脏卡？ 写屏障(Write Barrier)
~~~
Java代码   oldObject.field = youngObject;
在JVM编译后插入

1.执行复制
MOV [Address], Value

2.写屏障(AOP逻辑)
Mark_Card_Dirty(Address)


写屏障(Write Barrier)
    不是并发的Memory Barrier，它是JVM在每次"对象引用赋值"时，自动插入的一小段代码。类似于SpringAOP的 Around Advice。
    计算对象在Card Table中的索引，然后把那个位置的byte设为Diry[1]
    每次赋值多了几条命令，有一定的开销，但比FullGC扫描老年代还算
~~~

## 伪共享
~~~
Card Table是个byte数组。现代CPU缓存行(Cache Line)通常是64字节。一个缓存行可以存64个Card标志。

问题：多线程同时更新相邻的Card，虽然逻辑上不冲突，但物理上在同一个Cache Line，会导致缓存频繁失效，性能下降
解决：-XX:+UseCondCardMark 先检查是不是Dirty，是就不写了，减少写操作
~~~



## Major GC 、 Mixed GC 、 Full GC
~~~
Major GC（young GC）： 发生在新生代的垃圾回收，暂停时间短（STW）
Mixed GC  ： 新生代 + 老年代的部分区域的垃圾回收，G1收集器特有
Full GC ：  新生代 + 老年代完整垃圾回收，暂停时间长（STW）。应尽力避免

STW（Stop-The-World）：暂停所有应用程序线程，等待垃圾回收的完成
~~~

## 不同收集器的分代实现差异
| 收集器 | 新生代算法 | 老年代算法 | 特点 |
| :--- | :--- | :--- | :--- |
| Serial | 复制 | 标记-整理 | 单线程，简单高效，适合 Client 模式或小内存。 |
| Parallel Scavenge + Parallel Old | 复制 | 标记-整理 | 多线程并行，关注吞吐量（CPU 运行代码的时间占比）。 |
| CMS (Concurrent Mark Sweep) | 复制 | 标记-清除 | 关注低延迟，老年代并发收集，但会有碎片，JDK 9 已废弃。 |
| G1 (Garbage First) | 区域化复制 | 区域化混合回收 | 逻辑分代，物理不分代。将堆划分为多个 Region，动态扮演新生代/老年代角色。通过 Mixed GC 回收部分老年代 Region，避免 Full GC。 |
| ZGC / Shenandoah | 染色指针 / 读屏障 | 并发整理 | 新一代收集器。旨在实现亚毫秒级停顿。JDK 24 引入了 Generational ZGC/Shenandoah，重新引入了物理分代以进一步提升性能。 |
