# JDK 1.6 Java对synchronized同步锁做了充分的优化

## 修饰方法
~~~
1.JVM使用ACC_SYNCHRONIZED访问标识来区分一个方法是否为同步方法
2.在方法调用时，会检查方法是否被设置了ACC_SYNCHRONIZED访问标识
    如果是，执行线程会将先尝试持有Monitor对象，再执行方法，方法执行完成后，最后释放Monitor对象
~~~

## 修饰代码块
~~~
1.synchronized修饰同步代码块时，由monitorenter和monitorexit指令来实现同步
2.进入monitorenter指令后，线程将持有该Monitor对象，进入monitorexit指令，线程将释放该Monitor对象
~~~


## synchronized优化
~~~
1.JVM在JDK 1.6中引入了分级锁机制来优化synchronized
2.当一个线程获取锁时，首先对象锁成为一个偏向锁
    2.1: 这是为了避免在同一线程重复获取同一把锁时，用户态和内核态频繁切换
3.如果有多个线程竞争锁资源，锁将会升级为轻量级锁
    3.1: 这适用于在短时间内持有锁，且分锁交替切换的场景
    3.2: 轻量级锁还结合了自旋锁来避免线程用户态与内核态的频繁切换
4.如果锁竞争太激烈（自旋锁失败），同步锁会升级为重量级锁
5.优化synchronized同步锁的关键：减少锁竞争
    5.1: 应该尽量使synchronized同步锁处于轻量级锁或偏向锁，这样才能提高synchronized同步锁的性能
    5.2: 常用手段
            (1)减少锁粒度：降低锁竞争
            (2)减少锁的持有时间，提高synchronized同步锁在自旋时获取锁资源的成功率，避免升级为重量级锁
6.在锁竞争激烈时，可以考虑禁用偏向锁和禁用自旋锁
~~~

## 偏向锁的设置和被取消
~~~
禁用偏向锁
        VM 参数 -XX:-UseBiasedLocking
特殊情况:
        调用 对象的hashcode方法时,偏向锁也会被禁用. 这是因为调用了对象的 hashCode，但偏向锁的对象 MarkWord 中存储的是线程 id(54位)，如果调用 hashCode(31位) 会导致偏向锁被撤销
撤销 - 其它线程使用对象:
        当有其它线程使用偏向锁对象时，会将偏向锁升级为轻量级锁
批量撤销:
        当撤销偏向锁阈值超过 40 次后，jvm 会这样觉得，自己确实偏向错了，根本就不该偏向。于是整个类的所有对象 都会变为不可偏向的，新建的对象也是不可偏向的
锁消除优化:
        当执行的方法中的对象以及上锁的对象没有逃离方法的作用范围时,加锁与否并不会影响代码的执行速度,在这种情况下JVM底层是通过 解释+编译 的方式运行, JIT即时编译器 会对代码做优化, 在运行的代码超过一定域值时,该代码会变成热点代码(Hotspot),在此种锁情况下, JIT会默认将锁消除,当然也可以手动设置JVM参数:
        -XX:-EliminateLocks        消除锁消除优化
~~~



## 锁膨胀过程（偏向锁→轻量级锁→重量级锁）
~~~
锁膨胀是单向升级的过程，JVM 会根据线程竞争的激烈程度动态切换锁状态，从最省资源的偏向锁开始，仅当竞争出现并加剧时才逐步升级，最终在重度竞争时使用重量级锁。

1. 初始状态：偏向锁（无竞争场景）
适用场景：只有一个线程反复获取同一把锁，无任何其他线程竞争。

核心目的：消除无竞争时的 CAS 开销，最大化单线程执行效率。

实现原理：
    当线程第一次获取锁时，JVM 会通过 CAS 操作，将对象头 MarkWord 中的偏向锁标记设为 1，并记录当前线程的 ID（仅第一次获取需 CAS，后续无开销）；
    该线程后续再次获取锁时，只需检查 MarkWord 中的线程 ID 是否为自身，无需再次 CAS 或阻塞，直接进入临界区。

触发偏向锁撤销 / 升级的条件：
当其他线程尝试获取该锁时，偏向锁会被撤销（撤销时需暂停持有锁的线程）：
    若持有锁的线程已执行完毕，直接将偏向锁重置为无锁状态；
    若持有锁的线程仍在执行，偏向锁升级为轻量级锁。
    
补充：JDK 1.8 默认开启偏向锁，可通过-XX:-UseBiasedLocking关闭；偏向锁有延迟初始化（默认 4 秒），可通过-XX:BiasedLockingStartupDelay=0取消延迟。



2. 第一级膨胀：偏向锁→轻量级锁（轻度竞争场景）
适用场景：多个线程交替获取锁（无同时竞争），线程持有锁的时间较短。

核心目的：通过自旋 CAS 替代操作系统的阻塞 / 唤醒，减少线程切换开销。

实现原理：
    偏向锁撤销后，JVM 为获取锁的线程在其栈帧中创建锁记录（Lock Record），存储对象头 MarkWord 的拷贝；
    线程通过 CAS 操作，将对象头的 MarkWord 替换为指向自身锁记录的指针：
        CAS 成功：线程获取轻量级锁，进入临界区；
        CAS 失败：说明有其他线程竞争，当前线程会通过自旋（循环CAS）尝试获取锁。

触发轻量级锁升级的条件：
    自旋次数达到自适应自旋阈值（JDK 1.6 后自旋次数不是固定值，会根据前一次自旋的成功率动态调整）；
    自旋的线程数超过 CPU 核心数的一半，或持有锁的线程长时间未释放锁；
    此时 JVM 会将轻量级锁升级为重量级锁。
    
通俗类比：轻量级锁就像 “站在门口等锁”，线程不放弃 CPU 执行权，通过循环重试抢锁，避免了 “去休息室等” 的阻塞开销。



3.第二级膨胀：轻量级锁→重量级锁（重度竞争场景）
适用场景：多个线程同时竞争锁，或线程持有锁的时间较长。
核心实现：依赖操作系统的互斥量（Mutex）和线程阻塞 / 唤醒机制，通过 Monitor（监视器）对象管理锁的竞争。

实现原理：
    轻量级锁升级为重量级锁后，对象头 MarkWord 会被修改为指向Monitor 对象的指针；
    Monitor 包含_owner（锁持有者）、_count（重入次数）、_EntryList（等待队列）、_WaitSet（存放调用wait()方法后进入等待的线程）等核心字段：
        线程获取锁失败时，会进入_EntryList队列，放弃 CPU 执行权，进入阻塞状态（从用户态切换到内核态）；
        当持有锁的线程释放锁时，会唤醒_EntryList中的一个线程，使其重新竞争锁。
缺点：
重量级锁涉及用户态与内核态的切换，线程阻塞 / 唤醒的开销较大，但能有效处理重度竞争场景，避免自旋导致的 CPU 空耗。

通俗类比：重量级锁就像 “去休息室等锁”，线程主动放弃 CPU，直到被唤醒后再参与竞争，虽开销大但能节省 CPU 资源。



锁降级：synchronized 的锁膨胀是单向不可逆的，不存在 “降级”（如重量级锁不会变回轻量级锁），仅在 GC 时可能重置偏向锁状态；
锁消除：JVM 会对一些不存在竞争的同步代码块，自动消除锁（如局部变量的同步），进一步优化性能；
锁粗化：JVM 会将多个连续的细粒度锁合并为一个粗粒度锁，减少锁的获取 / 释放次数。
~~~

## MarkWord 关键字段说明
~~~
锁标志位：唯一区分锁状态的 “标识码”，01对应无锁 / 偏向锁、00对应轻量级锁、10对应重量级锁、11对应 GC 标记；
偏向线程 ID：偏向锁状态下，记录持有锁的线程 ID，实现 “线程偏向”（后续该线程获取锁无需 CAS）；
Lock Record 指针：轻量级锁状态下，指向线程栈中的锁记录（存储 MarkWord 拷贝，用于 CAS 抢锁）；
Monitor 指针：重量级锁状态下，指向对象关联的 Monitor 对象，通过 Monitor 管理线程阻塞 / 唤醒；
分代年龄：对象在新生代的存活次数，达到阈值（默认 15）进入老年代。
~~~

## Monitor
~~~
synchronized的实现分为代码块级和方法级，其中代码块级依赖monitorenter和monitorexit字节码指令，方法级则通过ACC_SYNCHRONIZED访问标志实现，二者底层均基于Monitor（监视器）机制（好比 “锁的管家”，管理锁的竞争与释放）。

1. Monitor：锁竞争的 “核心管理器”
    每个 Java 对象都关联一个 Monitor 对象（懒加载，仅当对象作为锁时创建），其核心结构包括：
        _owner：持有锁的线程 ID，初始为 null；
        _count：锁的重入次数，初始为 0；
        _EntryList：等待获取锁的线程队列（就绪状态）；
        _WaitSet：调用wait()后等待被唤醒的线程队列（阻塞状态）。
Monitor 的核心规则：同一时刻仅一个线程能成为_owner，其他线程需进入队列等待。

2. monitorenter 指令：获取锁的 “入口”
    该指令插入在synchronized代码块的起始位置，线程执行此指令时，尝试获取 Monitor 所有权，流程如下：
    1.读取锁对象的 MarkWord，判断锁状态（偏向 / 轻量级 / 重量级），对应不同的抢锁逻辑；
    2.尝试获取 Monitor 的_owner字段：
        若_owner为 null，将其设为当前线程，_count置 1，成功获取锁并进入临界区；
        若_owner为当前线程，说明是锁重入，_count加 1，直接进入临界区；
        若_owner为其他线程，当前线程进入_EntryList队列，放弃 CPU 执行权，进入阻塞状态。
        
3. monitorexit 指令：释放锁的 “出口”
    该指令插入在synchronized代码块的结束位置和异常处理位置（避免锁泄漏），线程执行此指令时，释放 Monitor 所有权，流程如下：
    获取锁对象关联的 Monitor，将_count减 1；
    若_count减至 0，说明完全释放锁：将_owner置为 null，唤醒_EntryList中的一个线程重新竞争锁；
    若_count仍大于 0（重入场景），仅减少计数，锁仍由当前线程持有。
    
    关键：JVM 会为每个synchronized代码块生成至少两个monitorexit—— 一个用于正常退出，一个用于异常退出，确保锁最终被释放。
    
    
4. 方法级 synchronized 的实现（ACC_SYNCHRONIZED）对于synchronized方法，JVM 不会生成monitorenter/monitorexit指令，而是在方法的访问标志中设置ACC_SYNCHRONIZED标记：
    线程调用方法时，JVM 检查该标记是否开启；
    若开启，线程需先获取方法所属对象（实例方法）或类对象（静态方法）的 Monitor，流程与monitorenter一致；
    方法执行完毕 / 抛出异常时，JVM 自动释放 Monitor，逻辑与monitorexit一致。
    
~~~
