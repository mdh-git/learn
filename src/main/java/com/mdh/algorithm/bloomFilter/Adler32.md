# Adler32
~~~
Adler32 是一种校验和算法（Checksum Algorithm），由 Mark Adler 于 1995 年发明，是 Fletcher 校验和的改进版。它常用于数据完整性检查（如 zlib 压缩库）

核心设计
Adler32：
目标：快速检测数据传输或存储中的意外错误（如比特翻转）。
特点：计算极快（尤其是短数据），但不抗碰撞攻击，且对于某些特定模式的数据（如大量零字节或重复模式），其分布均匀性较差。
Java 支持：JDK 原生支持 (java.util.zip.Adler32)。
~~~

## 优势
~~~ 核心优势
极致的速度（尤其是短数据）
    算法简单：Adler-32 的计算逻辑非常简单，主要涉及两个累加和（Sum A 和 Sum B）以及模运算。相比于 CRC-32 需要查表（Lookup Table）或进行复杂的位操作，Adler-32 的指令更少，流水线停顿更少。
    短数据王者：在处理小数据包（例如小于 4KB 的数据）时，Adler-32 的速度通常比 CRC-32 快 2~3 倍。这是因为 CRC-32 的查表操作在小数据上带来的开销占比更大，而 Adler-32 的纯计算模式启动更快。

实现极其轻量
    无依赖：不需要预先生成或存储巨大的查找表（CRC-32 通常需要 256 字节的表，虽然很小，但在极度受限的嵌入式环境中也是开销）。
    代码简洁：核心算法只需几十行代码即可实现，非常适合资源受限的环境。
    
~~~

## 用途
~~~
1. 压缩算法 (zlib / gzip / PNG)
    zlib 库默认使用 Adler-32 来校验压缩数据的完整性。
    原因：压缩和解压过程非常频繁，且通常处理的数据块较小。为了最大化压缩/解压速度，牺牲一点点检错能力（相比 CRC-32）是可以接受的权衡。PNG 图片格式也沿用了这一标准。
    
2.文件同步工具 (rsync)
    rsync 算法在判断文件块是否发生变化时，会使用“滚动哈希”。
    原因：rsync 需要在传输过程中实时计算大量数据块的哈希值。Adler-32 的计算速度极快，非常适合这种高频调用的场景，用于快速筛选出“可能相同”的数据块，然后再用更强的哈希（如 MD5）进行二次确认。

3. 内存数据校验
    在数据库（如 MySQL 的某些存储引擎）或内存缓存系统中，用于快速检测内存页是否在传输或存储过程中发生了比特翻转（Bit Rot）。
    
4. 嵌入式系统与固件
    在单片机或 IoT 设备中，如果 Flash 空间极其紧张，或者 CPU 主频很低，Adler-32 往往是首选的校验方案，因为它占用的代码空间和运行时资源最少。
~~~
