# Undo Log、Redo Log 和 Binlog
~~~
Undo Log (回滚日志): 事务的“后悔药”，保证原子性。
Redo Log (重做日志): 事务的“持久化保障”，保证持久性。
Binlog (归档日志): 数据库的“黑匣子”，用于复制和恢复。
~~~

| 日志类型 | 所属层级 | 核心作用 | 记录内容 |
| :--- | :--- | :--- | :--- |
| Undo Log | InnoDB 引擎层 | 保证事务的原子性，支持事务回滚和 MVCC。 | 逻辑日志，记录数据修改前的旧值或反向操作。 |
| Redo Log | InnoDB 引擎层 | 保证事务的持久性，用于崩溃恢复 (Crash Recovery)。 | 物理日志，记录数据页被修改后的物理状态。 |
| Binlog | MySQL Server 层 | 用于主从复制和数据恢复。 | 逻辑日志，记录所有引起数据变更的 SQL 语句或行变更。 |


## 协同工作：以一次 UPDATE 为例
~~~
假设执行一条更新语句：UPDATE user SET name = 'Li' WHERE id = 1; (原 name 为 'Wang')。整个流程清晰地展示了三大日志的配合。
~~~

### 1. 事务执行阶段：先留后路，再修改
~~~
1.生成 Undo Log: InnoDB 引擎在修改数据前，会先将原始数据（name='Wang'）记录到 Undo Log 中。这就像先备份，以便事务失败时能一键恢复。
2.修改内存数据: 在内存（Buffer Pool）中将数据页的 name 字段更新为 'Li'。此时，内存中的数据页与磁盘不一致，被称为“脏页”。
3.生成 Redo Log: 同时，将这次对数据页的物理修改操作记录到 Redo Log 中。
~~~

### 2.事务提交阶段：两阶段提交 (2PC)
~~~
这是保证 Redo Log 和 Binlog 一致性的核心机制。因为 Redo Log 在 InnoDB 引擎层，而 Binlog 在 MySQL Server 层，必须确保两者要么都成功，要么都失败。

1.Prepare 阶段:
    InnoDB 引擎将 Redo Log 写入磁盘，并将其状态标记为 PREPARE。
    通知 Server 层可以写 Binlog 了。

2.Commit 阶段:
    Server 层将本次事务的 Binlog 写入磁盘。
    Server 层通知 InnoDB 引擎：“Binlog 已写完”。
    InnoDB 引擎将 Redo Log 的状态从 PREPARE 更新为 COMMIT。

至此，事务才算真正提交成功。后台线程会在合适的时机将内存中的脏页异步刷到磁盘。
~~~

## 崩溃恢复：如何保证数据不丢不错？
~~~
当数据库意外宕机重启后，会根据 Redo Log 和 Binlog 的状态来决定如何恢复数据，这正是两阶段提交的价值所在。

场景 A：在 Redo Log Prepare 之后，Binlog 写入之前崩溃
    状态： Redo Log 是 PREPARE 状态，但 Binlog 中没有这条事务记录。
    恢复动作： MySQL 重启后检查发现 Binlog 不完整，为了保证主从数据一致（从库没收到），会判定该事务未成功，使用 Undo Log 来回滚此事务。

场景 B：在 Binlog 写入之后，Redo Log Commit 之前崩溃
    状态： Redo Log 是 PREPARE 状态，但 Binlog 已完整写入。
    恢复动作： MySQL 重启后检查发现 Binlog 中已有完整记录，说明 Server 层已确认提交。为了保证主库和从库（已收到 Binlog）的数据一致，主库会直接提交该事务，依据就是 Redo Log 中 PREPARE 的记录。
~~~

## 其他应用场景
~~~
主从复制： 主库将已提交事务的 Binlog 发送给从库，从库接收并重放（Replay），从而实现数据同步。这个过程只依赖 Binlog。
                                                                                                                                                               
数据误删恢复： 可以通过全量备份 + Binlog 的方式，将数据库恢复到误操作之前的任意时间点（Point-In-Time Recovery）。

MVCC (多版本并发控制): 在 RC 和 RR 隔离级别下，事务通过 Undo Log 中记录的旧值构建数据的历史版本链，从而实现非阻塞的快照读。
~~~
