
1.缓存击穿
    查询数据在数据库中不存在

    解决方案：
        1. 缓存空数据，设置一个过期时间，避免频繁访问数据库（消耗内存，可能会发生数据不一致）
        2. 布隆过滤器，（先查询布隆过滤器，后查询redis缓存）
            将所有可能存在的数据哈希到一个大的bitmap中，查询时先判断bitmap中是否存在，不存在则查询数据库，存在则返回缓存数据 （Redisson，Guava （设置误判率））
            存在误判的可能 : 增加布隆过滤器的数组大小，降低误判率（增大内存消耗）

在实际开发中，除非有极特殊的定制需求，否则强烈建议直接使用 Guava 库，它能帮你规避大部分底层实现的陷阱（如哈希碰撞、参数计算错误、线程安全问题等）。
Guava 使用的 MurmurHash 通常比 MD5/SHA 更快且分布更均匀。

1.速度极快、低碰撞率
    MD5/SHA：是加密哈希算法。它们的设计目标是“安全性”，即防止逆向破解、防止碰撞攻击。为此，它们引入了复杂的位运算和多轮迭代，计算开销大。
    MurmurHash：是非加密哈希算法。它的设计目标纯粹是“速度”和“低碰撞率”。它去掉了所有为了安全而增加的复杂逻辑，专注于快速混合数据位。
2.数据对比：
  在 Java 中处理相同长度的字符串，MurmurHash 的速度通常比 MD5 快 5~10 倍，比 SHA-256 快更多。
  对于布隆过滤器这种需要高频调用（每次 put 或 mightContain 都要计算 k 次哈希）的场景，哈希函数的速度直接决定了系统的吞吐量。

3. 分布均匀性（降低误判率）
    雪崩效应：MurmurHash 具有极好的雪崩效应（Avalanche Effect）。输入数据的微小变化（如改变一个比特），会导致输出哈希值发生巨大且不可预测的变化，且结果在整数空间内分布非常均匀。
    对布隆过滤器的意义：布隆过滤器的误判率高度依赖于哈希函数将元素映射到位数组不同位置的能力。如果哈希分布不均匀，会导致某些位被频繁置为 1（热点位），从而显著增加误判率。MurmurHash 的均匀分布特性使其成为布隆过滤器的理想选择。
    MD5/SHA 的过剩：虽然 MD5/SHA 的分布也很均匀，但这是为了抗密码学攻击而设计的“过剩能力”，在布隆过滤器中属于“杀鸡用牛刀”，且付出了巨大的性能代价。

3. Guava 的具体实现细节
Google Guava 并没有直接使用原始的 MurmurHash 算法，而是进行了针对布隆过滤器的优化：
    算法版本：Guava 主要使用 MurmurHash3（具体是 murmur3_32 或 murmur3_128 的变体）。
    多重哈希策略：
    1.布隆过滤器需要 k 个独立的哈希函数。
    2.计算K次完整的哈希非常慢。Guava 采用了一种巧妙的数学技巧（基于 Kirsch & Mitzenmacher 的理论）：只计算 2 个高质量的哈希值 (h1，h2),然后通过线性组合生成其余的k-2个哈希值。
    3.公式大致为：hash i（x） = h1（x） + i * h2（x）
        这种方法在保持理论上的低误判率的同时，将哈希计算的成本降低了近一半（无论 k 是多少，只需算两次主哈希）。



2.缓存穿透
    查询数据在数据库中存在，但缓存中没有（可能过期导致的）(热点key突然失效)

    解决方案：
        1.互斥锁（数据强一致性，性能差）
            查询未命中缓存的数据，加锁从数据库中获取，直到查到数据，重建缓存，写入缓存，释放锁 （只有一个线程可以访问数据库，别的线程需要等待）
        2.逻辑过期（高可用，性能优，不能保证数据绝对一致性）
            key:1  value:{"id":123,"name":"zhangsan","expireTime":1596816000000}}

            线程1： 查询缓存数据，发现逻辑过期，获取互斥锁，开启新的线程，返回过期数据
            线程2：                                    新的线程：查询数据库，重建缓存，写入缓存（更改逻辑过期时间），释放锁
            线程3：                       查询缓存，数据逻辑过期，获取锁失败，返回过期数据
            线程4：                                                                                                获取缓存数据，并且数据没有逻辑过期

3.缓存雪崩
    大量缓存数据在同一时间失效、redis服务器宕机

    解决方案：
        1.给不同的key的TTL添加随机值
        2.Redis集群提高服务的可用性（哨兵模式、集群模式）
        3.给缓存业务添加限流降级策略（nginx或者gateway）
        4.添加多级缓存（Guava或Caffeine）（先读取多级缓存，没有数据在读取redis）


4.数据一致性问题
    缓存与数据库数据不一致

    解决方案：
        1.延时双删（业务不复杂，对实时要求不高，有脏数据风险，不能保证数据绝对一致性）
            删除缓存数据，修改数据库，延时一会，删除数据库

        2.互斥锁
            1.添加分布式锁（Redisson）（性能比较低）
            2.读多写少的场景下可以使用Redis中的读写锁 （强一致性，性能低）
                共享锁： 读锁readLock，加锁之后，其他线程可以共享度操作
                排他锁：独占锁writeLock，加锁之后，其他线程不能读写操作，直到释放锁
            3.使用消息中间件MQ
                业务上修改数据时，写数据到数据库，并发送消息给MQ，监听到消息后，更新缓存
            4.使用Canal同步数据（基于mysql的主从同步来实现的，监听MySQL binlog日志）
