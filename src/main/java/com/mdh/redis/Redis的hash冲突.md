# Redis 的hash冲突

## 核心
~~~  
Redis的Hash类型底层使用两种编码:ziplist(压缩列表)和 hashtable(哈希表)。
当存储内容较多时，会使用 hashtable，其冲突解决采用经典的链地址法(拉链法)。
扩容机制采用渐进式rehash，以平衡性能与响应时间。
~~~

## Hash冲突的解决:链地址法
~~~
当Hash表发生冲突时，Redis的解决方案非常直观高效:
    数据结构:Redis的哈希表是一个 dictht 结构，内部包含一个 dictEntry 指针数组(俗称“桶”)，每个 dictEntry 是一个键值对节点，同时包含一个 next 指针。
    解决方式:当两个或更多的键通过哈希函数计算出的索引值(桶位置)相同时，Redis会将它们放在同一个桶里，通过 dictEntry 的 next 指针连接成一个单向链表。新加入的节点会被插入到链表的头部(时间复杂度O(1))。
    与Java HashMap的区别:Redis的哈希表没有红黑树转化机制。即使链表很长，也依然是链表。这是因为Redis是单线程模型，过长的链表会影响性能，所以Redis通过主动的扩容机制来严格控制链表的长度，防止其过长。

简单来说:哈希冲突->形成单向链表->头插法插入。
~~~

## 扩容机制:
~~~
Redis的扩容不仅仅是为了容纳更多数据，更重要的是为了维持较低的负载因子，减少哈希冲突，保证操作效率。

1.扩容触发条件
    触发扩容主要看哈希表的负载因子。
    负载因子 =已保存节点数量/哈希表大小。
    同时满足以下两个条件时，会触发扩容:
        1.负载因子>=1.
        2.服务器当前正在执行 BGSAVE 或 BGREWRITEAOF 等持久化命令,
            如果正在执行 BGSAVE/BGREWRITEAOF:为了避免父进程(主线程)进行大规模内存写入，造成与子进程的“写时复制”机制冲突，
            提高性能，触发扩容的负载因子阈值会提高到5。
            
简单记忆:平时1倍就扩容，后台持久化时5倍才扩容。


2.扩容大小
    新哈希表的大小是第一个大于等于原 used *2 的2的n次幂。例
        如，已使用 used=4，4*2=8，8正好是2的3次幂，新大小为8。如果used=5，5*2=10 ，则新大小为16(第一个大于10的2的幂)。
        
3.核心过程:渐进式Rehash
    一次性将所有键值对从旧表迁移到新表(像Java HashMap那样)会阻塞Redis单线程很长时间，导致服务不可用。因此Redis采用了渐进式Rehash
    
    步骤:
        1.准备阶段:为字典同时持有两个哈希表(ht[0]和 ht[1])。此时 ht[0]为旧表，ht[1]为新创建的空表。设置一个 rehashidx 变量，初始值为-1， 触发扩容修改为0，rehash正式开始。
        2.渐进迁移阶段(rehashidx>=0):
            每次对字典进行增、删、改、查操作时，Redis除了执行指定的操作外，还会顺带将 ht[0]中 rehashidx 索引对应的桶上的所有键值对链表，全部迁移到 ht[1]
            迁移完成后，将rehashidx值加1，指向下一个需要迁移的桶。
            此外，服务器每秒也会安排一个定时任务，主动迁移一部分桶，防止在空闲期长时间无法完成rehash。
        3.操作定位规则:
            在此期间，新添加的键值对一律会被保存到 ht[1]，保证 ht[0]的节点数只减不增。
            删除、查找、更新操作会同时在 ht[0]和 ht[1]上进行(先查 ht[0]，再查 ht[1])。
        4.完成阶段:当 ht[0]的所有桶都迁移完毕(即 rehashidx 等于桶数量)，将rehashidx 置为-1 ，释放 ht[8]的内存，将 ht[1]设置为新的 ht[0]，并在 ht[1]上新建一个空表，为下次rehash做准备,
~~~
