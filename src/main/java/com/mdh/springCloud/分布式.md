# 分布式问题

## CAP定理
~~~
一致性	      Consistency	           所有节点在同一时间看到的数据是相同的	         就像银行账户，你在任何 ATM 查询余额都应该一样
可用性	      Availability	           每次请求都能收到响应（无论成功或失败）	         就像 7x24 小时的便利店，任何时候去都能买到东西
分区容错性	  Partition Tolerance	   系统中部分节点之间的网络中断，系统仍能继续运行	 就像即使某条道路中断，交通系统仍能通过其他路线运行
~~~

## BASE 理论
~~~
BA	Basically Available	基本可用
S	Soft State	软状态
E	Eventually Consistent	最终一致性
~~~

## 解决分布式事务的思想和模型
~~~
1.最终一致思想:各分支事务分别执行并提交，如果有不一致的情况，再想办法恢复数据(AP)
2.强一致思想:各分支事务执行完业务不要提交，等待彼此结果。而后统一提交或回滚(CP)
~~~


## 分布式事务解决方案
~~~
1.Seata框架（XA、AT、TCC）
2.MQ
~~~

### Seata框架
~~~
TC	Transaction Coordinator:事务协调者	 总指挥部	独立部署的服务端，维护全局和分支事务的状态，驱动全局事务的提交或回滚
TM	Transaction Manager:事务管理器	     作战参谋	嵌入在应用中的客户端，定义全局事务的范围（开始、提交、回滚）
RM	Resource Manager:资源管理器	         前线部队	嵌入在应用中的客户端，管理分支事务，与TC通信汇报状态，执行提交/回滚
~~~

### XA模式—— 强一致、标准
~~~
基于数据库对XA协议的支持，是标准的两阶段提交实现

原理：
    一阶段：执行SQL但不提交，持有数据库锁
    二阶段：根据全局决议，统一提交或回滚
    
优点：强一致性，满足ACID，对业务无侵入（只需开启XA支持）
缺点：性能较差（锁资源直到二阶段结束），依赖数据库对XA的支持
适用场景：对数据一致性要求极高的场景，如金融核心账务
~~~

### AT模式（Auto Transaction）—— 无侵入、默认推荐
~~~
这是Seata的主打模式，也是最有特色的模式。

核心原理：
    一阶段：执行业务SQL，同时自动生成"前置镜像"（before image）和"后置镜像"（after image）记录到undo_log表，业务数据和undo_log在同一个本地事务中提交
    二阶段提交：直接删除undo_log，快速完成
    二阶段回滚：根据undo_log的镜像数据，生成反向SQL恢复数据，回滚前会校验是否有脏写

优点：对业务代码零侵入，只需在业务SQL上加@GlobalTransactional注解
缺点：有全局锁，性能略低于TCC；两阶段间是软状态
适用场景：大部分基于关系型数据库的业务，如订单、库存、账户等
~~~

### TCC模式（Try-Confirm-Cancel）—— 高性能、需编码
~~~
TCC是"补偿型"事务的典型代表，需要业务方自己实现三个方法

阶段	       方法	            作用
Try	       try()	     资源检查和预留（如冻结资金）
Confirm	   confirm()	 真正执行业务操作（要求Try成功则Confirm一定能成功）
Cancel	   cancel()	     释放预留资源，回滚操作

优点：一阶段提交本地事务后即释放资源，无全局锁，性能最高
缺点：代码侵入性强，需要自行实现三个方法，还要考虑空回滚、幂等、防悬挂等复杂问题
适用场景：高性能要求的场景，如金融转账、积分扣减等
~~~

### SAGA模式—— 长事务、异步
~~~
Saga是一种补偿协议，适用于业务流程长、涉及多个外部服务的场景

核心机制：
    将长事务拆分为多个本地事务，每个事务都有对应的补偿操作
    依次执行正向操作，如果某步失败，则反向依次执行补偿操作回滚
    通常是事件驱动、异步执行

优点：一阶段提交本地事务，无锁，高吞吐，适合长流程
缺点：不保证隔离性，补偿操作设计复杂，需要处理最终一致性
适用场景：业务流程长且需要最终一致的场景，如旅游预订、贷款审批等
~~~


### 总结
~~~
AT模式：零侵入、易用，适合大部分业务
TCC模式：高性能，适合核心交易链路
SAGA模式：长事务，适合复杂业务流程
XA模式：强一致，适合金融级场景
~~~
